## 0. 需求复述（请确认我理解无误）

你要做一个**出去玩时"去哪"的决策工具**，核心是一台**抽签转盘**。完整需求如下：

**① 数据来源**
- 写爬虫，从**高德、小红书等**平台抓取**评价**和**高德地址链接**。
- 抓到的链接要能**直接点击、浏览器打开就跳转到高德**（看店、看位置、去导航）。
- 抓取范围覆盖**一切出去玩可能去的地方**：景区、饭店、酒吧、KTV、麻将馆、爬山等。

**② 前置动作（已执行）**
- 先**测试哪些网站好爬、哪些不好爬**，不要盲目开工。
- 先只测**杭州**、每个类别抽一点，**不爬全量**，验证可行后再放大。
- 放大路线：**杭州 → 全杭州 → 全浙江 → 全国**。

**③ 转盘功能**
- **选地区**：可人工选定省或市；也可**随机城市/地区**。
- **选项目**：可人工选择项目；也可**随机项目**；项目集合按实际搜索结果动态调整。
- 项目示例：吃饭、酒吧、KTV、麻将馆、爬山……（**其中"吃饭/饭店"必须是人工选择时的必备选项**）
- 选定城市 + 项目后，进入**该城市该项目的抽签**（转盘转出具体一家店/一个地方）。

**④ 交付节奏**
- 以**杭州为试点**先跑通并打磨功能，再逐步扩展到全省、全国。

## 1. 可行性结论（基于实测，详见报告）

| 结论 | 说明 |
|---|---|
| 「点链接跳高德」 | ✅ 已验证，三种链接形态全部 200 且跳转正确 |

## 3. 数据模型

```sql
-- 行政区（省市）
region(id TEXT PK, name, level INT, parent_id, adcode, lng, lat)

-- 项目分类（转盘上的"项目"）
category(id TEXT PK, name, icon, group_name, amap_types TEXT, weight REAL)

-- 地点（核心表）
place(
  id TEXT PK,              -- = amap poiid（无则 'osm:'+id / 'seed:'+hash）
  source TEXT,             -- amap | osm | seed | manual
  region_adcode, city, district,
  category_id, name, address, lng, lat,
  rating REAL, cost REAL, tel, opentime,
  amap_url, uri_search_url, navi_url,
  raw_json TEXT, fetched_at, hot_score REAL
)

-- 评价（内容源聚合）
review(id PK, place_id, source, title, url, author, play_count, excerpt, created_at)

-- 用户足迹（本机个人数据）
visited(place_id PK, visited_at, rating_by_user, note)

-- 抽取历史（避免连着抽到同一家）
draw_history(id PK, place_id, category_id, city, drawn_at)
```

**高德链接生成规则（已验证）**
```ts
amapUrl  = `https://www.amap.com/place/${poiid}`                          // 有 poiid
uriUrl   = `https://uri.amap.com/search?keyword=${name}&city=${city}&view=map&callnative=0`  // 兜底
naviUrl  = `https://uri.amap.com/navigation?to=${lng},${lat},${name}&mode=car&policy=1`
markerUrl= `https://uri.amap.com/marker?position=${lng},${lat}&name=${name}&coordinate=gaode&callnative=1`
```

## 5. 转盘抽签设计（核心体验）

**两种地区模式**
- 人工：省 → 市 两级级联下拉（数据来自高德 district API，缓存本地）
- 随机：`随机城市`（全国/全省范围内随机取一个市）；`随机地区`（当前省内随机一个市）

**两种项目模式**
- 人工：多选（默认勾选"吃饭"且不可取消）
- 随机：从分类池按权重随机抽 1 个或多个

**抽签算法**
```
候选池 = places WHERE city=? AND category_id ∈ 选中项目 AND 未在最近 N 次抽中
权重   = base(category.weight) × rating因子 × (1 + hot_score) × 新鲜度因子
结果   = 按权重做轮盘扇区划分 → Canvas 绘制扇区 → 缓动旋转 4~6s → 指针落定
```
- 扇区数量：取候选池前 8~12 家（不足则全部），保证视觉合理
- 支持开关：`排除已去过`、`只看人均 < X 元`、`只看评分 ≥ 4.0`、`3 公里内`（需定位）
- 抽中后显示：名称、评分、人均、地址、**直接打开高德**、`再抽一次`、`就去这家`（写入足迹）

**公平性细节**：抽签用 `crypto.randomInt` 加密随机；权重只影响扇区大小，指针落点均匀随机，避免"看起来内定"。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 没有高德 Key | P2 无法开始 | P1 用种子数据 + OSM 兜底先跑通；Key 到位后无缝切换（采集器接口一致） |

| 小红书/点评拿不到 | 评价内容偏少 | B 站为主力；提供"粘贴分享链接"人工导入入口；结果卡直接给"去小红书搜这家"外链 |
| 高德 POI 分类码变化 | 随机项目抽空 | 分类配置与代码解耦（JSON），并加"关键词回退"（types 无结果时用 keywords 搜） |
| 反爬升级 | 采集失败 | 只依赖官方 API，永不依赖 HTML 逆向 → 天然免疫 |
| 合规风险 | 法律/封号 | 只用官方 API + 遵守 robots + 限速 + 个人自用 |

### 全国化才暴露的三个真实 bug

| bug | 现象 | 修法 | 效果 |
|---|---|---|---|
| 高德不认直辖市 adcode | `region=310100/500100/120100` **返回北京数据**，采"上海"得到一堆北京的店，还有"重庆 29 条"这种假象 | 直辖市改用城市名查询 + 首批结果不属于目标城市时自动回退 | 上海 87 → 1661 条，重庆 40 → 1598 条 |

### 全国规模与策略（重要）

- 全国 **392 个城市**，全量采集约 **6.3 万次请求（≈6 小时）**，**超出个人开发者免费日配额**
- 因此按设计走**按需采集 + 本地缓存**：用户抽哪个城市就采哪个城市
- 想扩某省：`npm run collect -- --scope china --province 广东省 --all --pages 2`
- 先看规模：`npm run collect -- --scope china --plan`（不发请求，打印每城预计请求数）

### 本轮修掉的三个真实 bug（都是测试逼出来的）

1. **种子数据陈旧行导致同一家店出现两次**：id 规则升级后老库残留旧 id（320 条），`ensureSeeded()` 原来"库里有数据就跳过"，导致 993 = 673 + 320 重复。改为：按种子 id 差集补灌 + 清理 `source='seed'` 的陈旧行（绝不动采集来的数据）。
2. **SQL 占位符数量不匹配**：`OR region_adcode IN (?)` 复用了同一批参数，多城市查询直接抛 `RangeError: Too few parameter values`；新增"空数组/单城市/多城市"边界测试防复发。
3. **同一条目同时挂在两个分类下**（酒球会 bar+livehouse、太子湾公园 sight+park），转盘上会出现两个同名扇区；种子生成器加入同城同名去重并打印去重日志。
