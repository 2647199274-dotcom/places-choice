# 区域维度筛选（美团式）

入口：`src/core/areas.ts`（聚合 + 交集过滤）、`/api/areas`、`/api/draw` 的 `areas` 参数。

## 四个维度与数据来源

| 维度 | 来源 | 键 | 备注 |
|---|---|---|---|
| `district` 地区 | `place.district` / `district_adcode` | adcode 或区县名 | 直接分组统计 |
| `businessArea` 商圈 | 高德 `business_area`（如"杭州新天地"） | 商圈名 | 覆盖率约 80% |
| `mall` 商场 | `typecode` 前 4 位 `0601` | 代表 POI 的 id | 用 **1.5km 包围盒**统计周边候选数 |
| `metro` 地铁 | `typecode` 前 4 位 `1505` | 站点 POI id | 与地点按**距离**关联（见下） |

## 关键实现点

1. **地铁是算出来的，不是高德给的**：高德 POI 没有"最近地铁站"字段。
   做法：采集地铁站 → 计算每个地点到各站的距离 → 取 ≤ **1200 米**内最近的一站，写入 `place_metro` 表。
   杭州实测：73 站、1209 条地点关联成功。改半径就改 `METRO_RADIUS_M`，改完重新 `npm run collect:areas`。
2. **多维取交集**（美团行为）：`filterPlacesByAreas()` 逐维过滤，某维结果为空立刻短路返回空。
3. **候选数量要跟着项目变**：`listAreas(city, dim, categoryIds)` 传入当前选中项目，
   这样"选了火锅再选区域"时，商场旁边的数量才是有意义的。
4. **商场名要归一化**：高德把同一商场拆成多条（`杭州湖滨in77` / `in77B区` / `in77C1区`…），
   `normalizeAreaName()` 去掉 `( )`、`X区/X期/X座/X号楼` 等后缀后合并——实测把 121 条压到 115 条。
   **注意不要过度合并**（`购物中心/广场/百货` 这类业态词要保留）。
5. **前端离线也要能筛**：`web/src/localDraw.ts` 的 `inAreas()` 用**区县名/商圈名**匹配；
   商场/地铁的关联关系只存在后端，离线时**不参与过滤**（宁可少筛，不可误杀）。
6. **前端 UI**：四个 `<details>` 折叠面板，选项按候选数降序，展示数量胶囊；已选项在下方以标签罗列，可单个移除或一键清空。

## 验收

```powershell
npm run test:areas        # 四维聚合 / 单维过滤 / 交集 / 空交集 / 字段覆盖率
npm run test:web          # 真实 Chrome：选中区域后抽签，结果必须落在该区域内
```
新增维度时，`verify-areas.mjs` 里要补一条"结果确实全部落在该区域内"的断言，不能只测数量。
